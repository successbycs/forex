# M33.3 recovery protocol

This protocol controls only the held, no-order listener recovery path. It does
not grant MT5, duplicate-client, broker, hold-release, or entry authority.

Each attempt is bound to a random request ID, monotonic generation, boot ID,
guardian/listener releases, governed configuration fingerprint, account/profile
hashes, observed-status digest, fixed action and short expiry. A request can
move only from `PENDING` to `CLAIMED`, `DISPATCHED`, then `VERIFIED`,
`REFUSED`, or `INTERVENTION_REQUIRED`. A lost, corrupt, expired or unresolved
request is intervention-required; it is never silently retried or replaced.

The ledger is atomic and monotonic. Corruption opens the circuit and preserves
the entry fence. The executor rechecks intent, hold, boot, release,
configuration, generation, request expiry and task ownership after obtaining
the shared recovery mutex and immediately before its one fixed listener task
action. It then requires fresh post-action listener, guardian, managed-process,
monitor/reconciliation and held-readiness evidence before recording `VERIFIED`.

An absent listener is preflighted from the prior immutable runtime binding, not
from a missing heartbeat. Any uncertain ownership, exposure, pending order,
unresolved submission or changed binding refuses the action. MT5 start/restart
and duplicate-client recycling require separately owned shared-platform
primitives and remain unsupported here.
