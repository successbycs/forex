# Proposed M20.13 amendment: pre-rollover entry cutoff

Prepared 2026-09-10. **Proposal only; not approved or applied to
`milestone_registry.json`.** It creates no new holding, closing or order
authority.

## Problem addressed

The current M20 owner exits are 6–10 minutes. Broker terms can apply swap at
the trading-day close, while the current account-specific fee arrangement and
rollover calendar are unqualified. An intraday entry close to rollover could
remain exposed past that boundary through ordinary execution delay or failed
recovery. A take-profit target or favourable projected swap is not evidence
that this exposure is acceptable.

## Proposed contract text

Add the following M20.13 operating constraint after operator approval:

> **Rollover entry boundary.** The fixed EURUSD Demo entry path must reject a
> new proposal if the next broker-qualified rollover event is less than 15
> minutes away. It must also reject a new proposal if that event is a weekend
> or public-holiday rollover. A rollover event is qualified only when the
> canonical policy names its broker source, covers the current broker server
> time and intended maximum owner-exit horizon, includes current DST/holiday
> treatment and specifies its day multiplier. Missing, expired, stale or
> unsupported calendar/fee inputs require `NO_TRADE`.
>
> **Existing exposure.** This boundary changes neither the existing 6–10
> minute strategy-owned exit, stop loss, take profit, maximum duration nor
> broker-side protection of an already-open position. If an attempted owner
> exit is failed, pending or uncertain, retain the broker protection, record an
> unresolved incident, and block dependent entries. It must never be recorded
> as closed from missing position data or a stale heartbeat.
>
> **Scope.** This is an intraday fallback only. It grants no discretionary
> overnight holding, no forecast-derived hold decision, and no exemption from
> fee-complete planned-loss, reservation or Option B checks. A later W3
> evidence-and-Demo-qualification decision is required before an overnight
> policy can be enabled.

## Basis and boundaries

The 15-minute cutoff is the longest current 10-minute owner exit plus a
five-minute execution/recovery margin. It is a safety margin, not an economic
return estimate. It must be evaluated from qualified calendar data, rather than
hard-coded server time or inferred from a historical zero-swap close.

The broker terms observed in the retained Demo capture report points-mode
EURUSD swap fields and a Wednesday triple flag. The official Mauritius
disclosure identifies close of trading day as 23:59 on the trading platform.
Neither source, alone, establishes this account’s exact commission arrangement
or a future calendar/DST/holiday schedule.

## Approval and implementation gates

Before a dependent code/configuration change:

1. The operator supplies or approves the exact account commission schedule and
   a dated broker-qualified rollover calendar source, coverage window, timezone
   and holiday/triple treatment.
2. The operator approves the proposed text or an explicitly recorded variant.
3. Astra completes the narrow pre-entry review using
   [the review packet](w1-pre-entry-review-packet.md), including any amendment
   change.
4. Terra updates the M20 contract, canonical configuration, code and tests
   under maintenance hold, then deploys and verifies the exact release.
5. Release eligibility is reassessed from fresh Demo exposure/audit state and
   all existing M20/Wave 1 gates. Passing this amendment alone cannot release
   entries or complete M20.

The proposal deliberately does not prescribe an account type, numerical fee,
rollover timestamp, holiday date or holding forecast. Those are external facts
that must be qualified rather than invented.
